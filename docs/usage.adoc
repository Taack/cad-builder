:icons: font
:toc:

`cad-dsl` does not depend on native code: parts and assemblies compiled against it can be shared as plain jars.
Running them needs a kernel: `cad-dsl-occt`, and `cad-dsl-native` built for the platform (see xref:building.adoc#native-library[Native Library]).

== Maven

Artifact coordinates:

.Maven
[source,groovy]
----
implementation 'org.taack.cad:cad-dsl:0.1'      // to write models
runtimeOnly 'org.taack.cad:cad-dsl-occt:0.1'    // to build them
----

NOTE: See https://github.com/Taack/cad-dsl-app/blob/main/cad-dsl-linux-app-x86-64/build.gradle[sample-build.gradle] to deal with JMOD files

Build `cad-dsl-native` for your platform (see xref:building.adoc[Building]), and put its directory in `java.library.path`.

== Scripts

`cad-dsl` runs a model written as a Groovy script, without any project or test around it.
The DSL packages (`org.taack.cad.dsl`, `.geom`, `.helper`), `CadDsl.cd()` and `java.lang.Math` are imported for the script:

.sphere.groovy
[source,groovy]
----
cd().position(new Vec(0, 0, 1)) {
    sphere(sqrt(4))
}.display(args ? args[0] : null)
----

[source,bash]
----
./gradlew :cad-dsl-occt:installDist   # or distZip, to share it
cad-dsl-occt/build/install/cad-dsl/bin/cad-dsl sphere.groovy              # <1>
cad-dsl-occt/build/install/cad-dsl/bin/cad-dsl sphere.groovy sphere.step  # <2>
----

<1> Opens the shape in the viewer.
<2> The arguments following the script are available as `args`; this script exports to the file given.

`cad-dsl` passes `CAD_DSL_OPTS` and `JAVA_OPTS` to the JVM: set `java.library.path` there (see xref:building.adoc#native-library[Native Library]).

[source,bash]
----
export CAD_DSL_OPTS="-Djava.library.path=$PWD/cad-dsl-native/build/lib/main/release"
----

From Gradle, `./gradlew :cad-dsl-occt:run --args="$PWD/sphere.groovy"` sets it to the library just built.

Classes in the directory of the script are found too (`Contour.groovy` for a class `Contour`), to share parts
between scripts.

=== Classes in `@CompileStatic`

A class of parts compiled with `@CompileStatic` is checked when the script starts, and reads like Java. In the closures
of the DSL, `delegate` is typed by their `@DelegatesTo`: `part(name) { bay(delegate, z) }` passes the `CadDsl` of the
part to a method `bay(CadDsl dsl, double z)`.

The DSL takes `double`, and a decimal literal is a `BigDecimal` in Groovy: it is converted where a `double` is
expected, as an argument (`box(1.5, 2, 0.8)`, `new Vec(z - 7.5, 0, 0)`) or in an assignment (`double h = 1.5`).
A conditional mixing both is not:

[source,groovy]
----
double ribFrom = first ? zMin : z - 8.792    // rejected: Number & Comparable, neither double nor BigDecimal

double ribFrom = first ? zMin : z - 8.792d   // accepted: a double literal

double ribFrom = z - 8.792                   // accepted: an if
if (first) ribFrom = zMin
----

The type the checker gives to `cond ? a : b` (or `a ?: b`) is the common supertype of both branches; with a `double` on
one side and a `BigDecimal` on the other, it is `Number & Comparable`, which no `double` parameter accepts. A `d` suffix
on the literals of the conditional, or `as double` around it, gives it a `double`.

To get code completion, write the imports anyway (`import org.taack.cad.dsl.geom.Vec`, `import static org.taack.cad.dsl.CadDsl.cd`…) and open the scripts
in a project depending on `org.taack.cad:cad-dsl` only.

[[runner]]
== Runner

`cad-dsl-runner` runs scripts for an IDE, in a JVM that stays up between the runs. Started with a port, it connects to
it on the loopback interface, reads one JSON request per line, and answers with one JSON event per line:

[source,json]
----
{"type": "run", "id": 1, "script": "/models/rail.groovy", "args": [], "params": {"length": 120}, "classpath": ["/m2/parts-0.1.jar"], "stopAt": "assembly:rail/part:body/cut0"}
{"type": "display", "id": 1, "file": "/tmp/cad-dsl-runner.../run-1/1.glb", "feature": "assembly:rail"}
{"type": "done", "id": 1, "params": {"length": 120.0}, "millis": 840, "features": [...], "stopAt": "assembly:rail/part:body/cut0"}
{"type": "shape", "id": 2, "feature": "assembly:rail/part:body/cut0"}
{"type": "shape", "id": 2, "file": "/tmp/cad-dsl-runner.../run-1/shape-2.glb"}
----

The `display()` calls without a file name write binary glTF files instead of opening the viewer (see `CadDisplay`): a
mesh per part, once however many times it is placed, with its faces (triangles) and their boundaries (lines); a node per
part or assembly placed, named after it; an animation channel per moving component. The model is turned from
millimeters and Z up to meters and Y up, as glTF expects (see `write_glb_assembly` in `occt_capi.h`).
`params` set the `param()` values of the script, and `classpath` adds jars and directories of classes to its own, for
this run only: the shared parts it uses (see <<sharing-parts>>). `features` is the tree of the operations of the script,
recorded while it runs (see `CadFeatureRecorder`): assemblies, parts, booleans, prisms, sketches, each with the file and
line that made it, those built by a method of the user grouped under it; up to the failing one, marked with `"error":
true`, when the run fails. A display event names the feature it shows, and a `shape` request writes the shapes of a
feature of the last run (a primitive, a prism, the tools of a cut...) to a glTF file, in the coordinates of its part.
`stopAt`, optional, rolls the script back to a feature of the last run of the same script: the operations after it are
recorded, marked with `"suppressed": true`, but not done. Within a solid, only the operations of that solid stop, and the
solid is shown in its assembly as it was at that feature; at a part, a placement or a solid, all the following ones stop.
The end event repeats `stopAt` when the last run had that feature, the run goes to its end otherwise.
The protocol is described in `CadRunner`.

[source,bash]
----
./gradlew :cad-dsl-runner:installDist
JAVA_OPTS="-Djava.library.path=$PWD/cad-dsl-native/build/lib/main/release" \
  cad-dsl-runner/build/install/cad-dsl-runner/bin/cad-dsl-runner <port>
----

The runner uses the OCCT kernel.

== Code Completion

The DSL is statically typed: completion needs an IDE supporting Groovy `@DelegatesTo`, such as IntelliJ IDEA Community.
It only needs `cad-dsl` on the classpath, neither OCCT nor native code. Scripts run by `cad-dsl` or the runner get imports
they do not write (see `CadScript`): the <<intellij-plugin,IntelliJ plugin>> declares them to the IDE.

== IntelliJ Plugin

`cad-dsl-intellij` is a plugin for IntelliJ IDEA 2026.2 and later, free edition included:

* *CAD scripts*: the Groovy scripts of a module with `cad-dsl` on its classpath, and the scripts named `*.cad.groovy`.
They resolve without the imports `CadScript` adds when it runs them, read from `script-imports.properties` in `cad-dsl`.
* *CAD Script run configuration*, from the run icon on the first line of a script: the module of the script is built,
then the script runs in `cad-dsl-runner`, out of the IDE, with the classpath of its module (see <<sharing-parts>>). Its
output goes to the Run tool window. Stopping the run stops the runner.
* *CAD Preview tool window*: the models the `display()` calls of the last run wrote, shown with three.js in the IDE
browser (JCEF). Orbit, fit, edges on or off, and a time bar for the animations. Saving the script, or a class of its
directory, runs it again. Clicking a part, without dragging, selects it in the CAD Structure and opens the line that
made it; for a part of a jar of parts, the line that placed it in the assembly. Clicking nothing selects nothing.
* *CAD Structure tool window*: the tree of the features of the last run. Double-clicking a feature, or Enter, opens the
line that made it, in the script, a class beside it or a class of a jar of parts; moving the caret of an editor to a line
selects the feature it made, unless _Follow Editor_ is off. The edges, arcs and texts of the
sketches are hidden unless asked for; the failing feature of a failed run is selected, in red. Selecting a feature
highlights its part in the preview, in every place the part occupies, fades the others, and draws the shapes of the
feature over it, through the solid: the primitive, the prism or the tools of a cut, with the OCCT kernel. _Roll Back
Here_, in the toolbar or the context menu, runs the script up to the selected feature, as SolidWorks does: a bar goes
under it, the features after it are grayed, and the preview shows the model as it was. The following runs of the script
stop there too, until _Roll Forward_, or until the script no longer has that feature.

The runner and the native library are found in the project when it is cad-builder, after:

[source,bash]
----
./gradlew :cad-dsl-runner:installDist :cad-dsl-native:linkRelease
----

Elsewhere, set them in _Settings | Tools | CAD DSL_, with the Java 25 running the runner (the runtime of the IDE by default).

[source,bash]
----
./gradlew :cad-dsl-intellij:runIde        # an IDE with the plugin
./gradlew :cad-dsl-intellij:buildPlugin   # build/distributions/cad-dsl-intellij-0.1.zip, to install from disk
./gradlew :cad-dsl-intellij:test          # with the runner: -PrunnerTests -PocctHome=<OCCT install>
----

`cad-dsl-intellij/example` is an empty Gradle project to try the plugin, with parts shared as a jar: see its README.

== Sharing Parts as Jars

The purpose of the DSL is to share parts and assemblies like Java class binaries. A part is a class written with the DSL,
in an ordinary Groovy library depending on `cad-dsl`:

.parts/src/main/groovy/org/example/parts/Plate.groovy
[source,groovy]
----
package org.example.parts

import org.taack.cad.dsl.CadDslSolid
import org.taack.cad.dsl.geom.Vec

import static org.taack.cad.dsl.CadDsl.cd

class Plate {
    static CadDslSolid drilled(double length, double width, double thickness, double holeDiameter) {
        double inset = holeDiameter * 1.5
        cd().box(length, width, thickness).cut {
            [new Vec(inset, inset, 0), new Vec(length - inset, inset, 0)].each { Vec hole ->
                position(hole) { cylinder(holeDiameter / 2, thickness) }
            }
        }
    }
}
----

.parts/build.gradle
[source,groovy]
----
plugins {
    id 'groovy'
    id 'java-library'
    id 'maven-publish'
}

group = 'org.example.cad'
version = '0.1'

dependencies {
    api 'org.taack.cad:cad-dsl:0.1'
}

publishing {
    publications {
        maven(MavenPublication) { from components.java }
    }
}
----

The library compiles without OCCT nor native code: its jar holds the classes of the parts, and is published to a Maven
repository, `./gradlew publishToMavenLocal` for the local one. Unlike the scripts, the classes write their imports:
the DSL ones are only added to the scripts.

A project uses the parts as any dependency. In the IDE, the scripts get completion on them; when it runs a script, the
IntelliJ plugin sends the classpath of the module of the script to the runner (`classpath` of the run request, see
<<runner>>): the jars Gradle resolved, and the classes of the modules it depends on, built before the run. The plugin
resolves nothing itself, Gradle does.

The classes of the runner come first: `cad-dsl`, Groovy and the kernel are those of the runner whatever version the
project depends on. The parts must be compiled against the `cad-dsl` the runner runs, else a method changed in between
fails at runtime.

A part published again under the same version is taken by the next run: the runner opens the jars again for each run.
A new version, or a new library, needs the Gradle project reloaded in the IDE.
